The road from 6 sheets to 27

RVTools ships 27 worksheets. STTools ships six. This is where the gap sits, which piece of architecture decides how expensive closing it will be, and the order that costs the least.

The decision that sizes everything else

One inventory walk per sheet does not survive 27 sheets

Four sheets each call retrieve("VirtualMachine", ...) on their own, and common.rs adds two more walks for host names and per-host VM totals. Five sheets currently cost roughly six full inventory passes.

today: 6 passes for 5 sheets
same approach at 27 sheets

Ten of the 27 sheets are derived from VirtualMachine properties. Fetch once per vCenter per export instead, into a snapshot the sheets read from: 

InventorySnapshot {
    vms:         Vec<ManagedObject>,   // union of every sheet's VM property set
    hosts:       Vec<ManagedObject>,   // union of every sheet's host property set
    datastores, clusters, resource_pools, dvswitches, ...
}

Each sheet becomes fn rows(&InventorySnapshot) -> Vec<Vec<Cell>>. The second payoff matters as much as the speed: a sheet that is a pure function over a snapshot is testable against one captured XML fixture, with no live vCenter. Today only vHealth (8 tests) and vSnapshot (1 test) have any.

The phases

Numbered because the order is load-bearing, not for decoration: Phase 0 is what makes Phases 1 to 4 cheap, and Phase 5 is gated on query patterns that do not exist yet.

1VM sheets

Seven sheets off one snapshot

vCPU, vMemory, vTools, vNetwork, vPartition, vCD and vUSB all read the same VM snapshot. No new query pattern, no new object type. This is the cheapest large block of parity in the plan, and small per sheet once Phase 0 exists.

6The product

Parity is not only sheets

RVTools does all of this. STTools does none of it yet.

  • Headless export. RVTools' -c ExportAll2xls is how people schedule it, and it is also the README's Linux-service goal. Needs a second binary, which is why default-run matters.
  • CSV export per sheet, alongside xlsx.
  • Email delivery of a finished export over SMTP.
  • Zip and password-protect the export.
  • Search, filter and column sort in the grid.
  • Connect straight to a standalone ESXi host, not only to vCenter.
  • Custom attributes and vSphere tags as columns.

Carry these alongside, not afterwards

Security

Stored passwords are cleartext

config.json holds vCenter passwords as plain strings. restrict_permissions chmods it to 0600, but only on Unix: the #[cfg(not(unix))] arm is an empty function, so on Windows, a first-class target here, the file gets default ACLs.

RVTools encrypts its stored passwords. Move to the OS credential store.

Security

Authenticate the web service

If the Linux service mode in Phase 6 happens, it needs auth from the first commit. The reference implementation bound 0.0.0.0 with no auth and an endpoint that returned stored vCenter credentials in cleartext.

That defect is documented. Do not inherit it.

Blocked

No vCenter to develop against

The documented lab, vcsa91.vcrocs.local, belongs to the original author and does not resolve (checked: NXDOMAIN). Every new sheet needs live queries before its property paths can be written.

This blocks Phase 1, and no amount of Rust solves it.

Open question

Which RVTools version is the target?

The column spec was derived from the export in reference/, which is RVTools 4.6 from August 2024. Every count on this page is sized against those lists.

If the target is a newer shipping release, generate a fresh export and re-derive the sheet and column lists before Phase 1 starts.

Recommended first slice

Phase 0 items 1 and 2, then all of Phase 1

One architectural change plus seven sheets that share a single code path. It moves the app from 6 sheets to 13, adds Datacenter, Cluster and Folder to every sheet at once, and produces the fixture corpus that makes Phases 2 to 4 testable without a live vCenter for every change.
